WHY

Process is global. Product is local.

This repository ships the process — reusable rules, agent roles, workflows and templates. It carries no project’s requirements. OpenSpec lives inside each project’s own repo, so a global instruction never leaks a product decision, and one project’s rules never contaminate another.

discovery

Explores the domain, writes the PRD and bounds vague ideas.

openspec

Scaffolds a validated change: proposal, spec deltas, scenarios.

architect

Decides boundaries, contracts and rejected alternatives; writes ADRs.

planner

Breaks the change into granular, verifiable tasks.

builder

The only stage that writes code, in batches of tasks with tests.

reviewer

Adversarial review of the diff against the spec.blocks

qa

Validates real behavior against the spec scenarios by executing them.blocks

release

Release notes, OpenSpec archive, final repo state.

THE GATE

No code without a validated change.

Every agent’s output is re-verified in the repo before the next stage. Only reviewer and qa can block progress. Two failures with the same error means the spec is wrong — the loop goes back a stage, never in circles.

USAGE

Pick the trigger that matches the change.

Hermes classifies every request into one of three task levels and runs the matching path. Copy-paste scenarios live in the repo’s docs/usage-examples.md; here is the shape of each.

feature

Full — a business rule, a contract, or architecture. Whole loop: analysis → spec → plan → code → review → QA → release. Starts with discovery of the problem.

bugfix

Minimal — a bounded fix that changes behavior. Runs the fast path (skip_specs) but always carries a regression test that fails without the fix.

fix

Cosmetic — no observable behavior change. A direct edit; there is no OpenSpec change because there is nothing to verify at spec level.

do

Autonomous — run the whole loop end-to-end with no human in the loop, ending in a PR for review. A confidence gate stops on non-trivial decisions.

# the trigger does not depend on exact wording $ hermes > let’s run SDD: add SSO login to the web app > fix the invoice total — it rounds wrong when the tax is 21% with decimals > rename the local variable dat to data in src/parser.ts
FAQ

Frequently asked questions.

Do I need OpenSpec installed to use it?

Yes. The loop is built on the OpenSpec CLI (openspec), ≥ 1.13.0, on your PATH (e.g. ~/.local/bin/openspec). Hermes runs it from each project root.

Do I have to install all the bundles?

No. /agency loads the orchestrator plus openspec-sdd; the per-stage commands are convenience entry points. The installer installs all 13 by default, but --bundles a,b,c selects a subset.

Can two agents talk to each other?

No. Agents never talk to each other and never read each other’s state. Every output returns to Hermes in the mandatory envelope and is re-verified in the repo. Hermes is the only bus.

Who can block progress?

Only the reviewer (changes-requested) and the qa agent (fail). Open BLOCKER/MAJOR, a qa: fail or any blocked halts the workflow.

Do I have to write the spec prose by hand?

No. The openspec stage’s agent writes the change artifacts via the CLI. You supply the idea and the repo; Hermes and the stage agents produce the proposal, spec deltas, design, tasks and code.

Can I use this on several projects at once?

Yes. Each project is a separate workflow with its own root, change and final report. Hermes runs independent stages in parallel via delegate_task and never mixes context across projects.

Full Q&A in the repo’s docs/FAQ.md.

ADVANCED

Configure for how you actually work.

Beyond the one-command install and the default triggers — flags, autonomy and the fast paths for when you want to tune the process.

Install flags

Target a custom home with -p <dir> (honors $HERMES_HOME), install a subset with --bundles a,b,c, skip bundles with --no-bundles, preview with --dry-run, and confirm non-interactive installs with -y.

The confidence gate

/do and /continue run routine decisions automatically (recorded as ADRs flagged ASSUMED) but stop and wait on non-trivial ones: contract/API, data model, real security risk, high cost to revert.

Parallel workstreams

Run independent changes in separate git worktrees, each with its own root and report. Independent stages fan out via delegate_task; overlapping file sets run sequentially.

Verifiable evidence

bin/no-smoke-worktree fingerprints the working tree (a content hash that survives rebase/amend but changes on any source change). Reviewer, QA and release record it and release-change compares — no smoke, no “I validated it” over older content.

Fast paths

Refactors, low-risk fixes and tooling use skip_specs: true (a validated change, minus requirement deltas). A cosmetic level touches no behavior and skips the loop entirely.

PRINCIPLES

Rules that are never broken.

1

No implementation code without a validated OpenSpec change in the project.

2

OpenSpec lives in each project’s repo, never in Hermes.

3

Agents never talk to each other; every output goes to Hermes, which validates.

4

Evidence beats assertion — an agent’s output is a self-report, re-verified in the repo. Reviewer, QA and release stages bind their evidence to the exact tree via bin/no-smoke-worktree (a content fingerprint), so a stage can never claim it validated content it never saw.

5

Product requirements are never global truth; they live in the project’s specs and ADRs.

6

Every report declares its projectRoot, matched against the verified root.

7

Only reviewer and qa can block; a blocker closes only with new evidence.

8

Everything the system produces is English; the only exception is the conversation with the user.
